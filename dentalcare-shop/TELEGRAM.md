# Telegram DentalCare — настройка и результаты

Проверено 4 ноября 2026 года. Изменения находятся в рабочей копии; они не опубликованы на вашем сервере автоматически.

## Причины неисправности

В среде нет `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`; нет и настроек Supabase. Исходный проект содержал только исходящую отправку `sendMessage`. Обработчика обновлений, `/start`, команд и процесса polling не было. Поэтому открытие контакта по телефону не являлось запуском бота. Номер **+996502820642** сохранён, но он не заменяет токен и ID чата.

## Исправления

- Серверный транспорт `api/_telegram.js`: таймаут 10 секунд, проверка HTTP и `ok`, безопасные коды ошибок для 400/401/403/429, сетевых сбоев и повреждённого ответа. Токен и URL с токеном не возвращаются клиенту и не печатаются в логах.
- Уведомление отправляется после успешной транзакции Supabase, исключительно на серверный `TELEGRAM_CHAT_ID`. Передаются полный UUID заказа, имя, телефон, email, товары, количества, цены, сумма, адрес, комментарий, дата/время по Бишкеку (UTC+6). HTML пользовательских полей экранирован. Длинные товарные названия ограничены в уведомлении, полные данные сохраняются в заказе. Ограничены длины контактных полей, чтобы сообщение укладывалось в лимит Telegram.
- Ошибка Telegram не отменяет заказ и не списывает остатки повторно; покупателю показывается честный результат доставки. Необязательная запись статуса уведомления не превращает сохранённый заказ в ошибку оформления.
- `place_order_once` и request ID формы защищают повторную отправку той же попытки: тот же пользователь и ключ получают прежний заказ, без второго списания и уведомления. Изменённые данные с тем же ключом отклоняются (409). Клиент сохраняет ключ до завершения текущей попытки на странице; перезагрузка страницы создаёт новую попытку. Старые внешние клиенты без `request_id` сохраняют совместимость, но не получают эту защиту.
- Webhook `/api/telegram-webhook`: POST, проверка `X-Telegram-Bot-Api-Secret-Token` через timing-safe сравнение, закрытый доступ без настроек, валидация update ID. Принимаются только сообщения из настроенного административного чата. Произвольные чаты игнорируются без доступа к заказам.
- Команды `/start`, `/help`, `/status` и понятный ответ на другой текст. Меню команд регистрируется скриптом настройки. Это **административный бот уведомлений**, не публичный магазин внутри Telegram: он не принимает заказы из переписки и не рассылает подтверждения клиентам, чьи Telegram ID неизвестны.
- Таблица `telegram_updates` хранит только update ID и время, без переписки; доступна лишь service_role. Повторно доставленный update не вызывает второй ответ. Если сеть оборвалась неоднозначно, автоматический повтор отключён: Telegram мог принять сообщение. После явного отказа API claim снимается для последующего повтора.
- Добавлены безопасная диагностика, настройка webhook без сброса pending updates и отдельная команда тестовой отправки. Polling не используется: не запускайте второй обработчик `getUpdates` для этого бота.

## Что нужно добавить в защищённые настройки

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Токен существующего бота из BotFather; только backend |
| `TELEGRAM_CHAT_ID` | Числовой ID нужного административного чата; минус у групп сохраняется |
| `TELEGRAM_WEBHOOK_SECRET` | Собственный случайный секрет 32–256 символов A–Z/a–z/0–9/_/-; только backend |
| `SITE_URL` | Настоящий публичный HTTPS-origin сайта без пути, query и fragment |
| `VITE_SUPABASE_URL` | URL проекта; frontend при сборке |
| `VITE_SUPABASE_ANON_KEY` | Публичный anon/publishable key; защищён RLS |
| `SUPABASE_URL` | Тот же проект; backend |
| `SUPABASE_SERVICE_ROLE_KEY` | Серверный service_role key; никогда не VITE_ |

Не присылайте секреты в чат и не коммитьте `.env`. Добавьте их в защищённые переменные хостинга. Токен не нужен в frontend. Если токен когда-либо публиковался раньше, отзовите его через BotFather; отсутствие ключей в текущем frontend не доказывает чистоту всей истории Git.

## Порядок включения

1. Для новой базы сначала `supabase/schema.sql`. Для существующей базы сохраните резервную копию и исходные данные.
2. Примените обновлённый `supabase/checkout.sql` (включая `place_order_once`) и затем **`supabase/telegram.sql`**. Только после этого публикуйте API.
3. На хостинге задайте переменные выше. Для теста на локальной машине допустим исключённый из Git `.env`. Node.js 24+, `npm ci`, `npm run build`, `npm start`. Подробности HTTPS и Vercel — в `PRODUCTION.md`.
4. Администратор должен открыть своего бота и нажать Start. Для группы добавьте бота и разрешите отправку сообщений; используйте числовой ID именно этой группы. Системные сообщения из чужих чатов бот намеренно игнорирует.
5. Из корня приложения с защищёнными переменными выполните:

```sh
npm run telegram:check
npm run telegram:setup
npm run telegram:test
```

`check` вызывает только getMe/getChat/getWebhookInfo; `setup` меняет webhook и меню команд; **`test` действительно отправляет одно тестовое сообщение в настроенный чат**. Для генерации секрета на своём доверенном сервере можно выполнить `node scripts/setup-telegram.js secret` и сохранить результат в защищённой настройке; не публикуйте вывод.

6. В административном чате отправьте `/start`, `/help`, `/status`. Проверяйте, что отвечает именно ваш бот. `telegram:check` показывает наличие webhook, очередь и наличие последней ошибки без публикации URL/секретов.
7. Через сайт зарегистрируйте тестового пользователя, добавьте товар, создайте **один** явно обозначенный тестовый заказ. Проверьте UUID, итог и `stock_reserved` в Supabase, уменьшение остатка, фактическое получение уведомления и все поля. Отмените этот заказ через админку и проверьте возврат остатка. Убедитесь, что повтор того же `request_id` возвращает тот же заказ и не создаёт ещё одно сообщение.

Для отправки сообщений нужен исходящий HTTPS к `api.telegram.org`; для базы — к вашему Supabase. Webhook должен быть доступен Telegram по публичному HTTPS без Basic Auth, но с проверкой секретного заголовка внутри обработчика.

## Не подтверждено без ваших настроек

`npm run check:services` завершился кодом **2**: отсутствуют ключи Telegram и Supabase (также отсутствуют настройки Email). Настоящие getMe, getChat, sendMessage, сохранение в вашей Supabase и получение сообщения человеком не выполнялись. Локальные SQL-тесты действительно создавали заказы в отдельной временной базе; это не ваш production.

Нельзя гарантировать exactly-once доставку внешнего API при аварии между отправкой и записью метаданных. Автоматическая очередь повторов уведомлений и восстановление после остановки процесса не реализованы; при сбое статус доставки остаётся отрицательным/неизвестным. Не создавайте новый заказ только ради повтора уведомления: проверьте сохранённый заказ в админке. Полный живой цикл нужно подтвердить после настройки и публикации текущих файлов.
