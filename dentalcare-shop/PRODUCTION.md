# DentalCare-shop: запуск в production

Проверенная конфигурация: Node.js 24.22.1, PostgreSQL 17 для SQL-проверок, собранный Vite frontend и Express API на одном origin. Реальные Supabase/Telegram/Resend в текущей среде не подключены.

## 1. Используйте версию с исправлениями

Корень приложения — **`dentalcare-shop` внутри репозитория DentalCare-shop**. Здесь находятся `package.json`, `api/`, `server/`, `supabase/` и `vercel.json`.

Перенесите текущие исправленные файлы на хостинг или сначала сохраните их в своей ветке Git. Клонирование старого `main` до сохранения исправлений не переносит изменения из этой рабочей копии.

Нужны Node.js 24.x и npm. Проверьте `node --version`. TypeScript в проекте не используется: исходники JavaScript/JSX.

## 2. Подготовьте Supabase до публикации API

Для **нового** проекта последовательно выполните в Supabase SQL Editor:

1. `supabase/schema.sql` — таблицы, RLS, триггер профиля и исходные товары.
2. `supabase/checkout.sql` — транзакционное оформление, склад и защита повторных запросов.
3. `supabase/telegram.sql` — закрытая таблица дедупликации webhook, если включаете команды бота.

Для **существующего** проекта сначала сделайте резервную копию, проверьте наличие базовых таблиц и примените обновлённый `supabase/checkout.sql`, затем `supabase/telegram.sql` для команд бота. Не создавайте новый проект вместо существующей базы и не очищайте таблицы. Повторное применение известных скриптов проверено на сохранение данных, но собственные изменения схемы и политик следует просмотреть перед применением.

Важно: `schema.sql` содержит исходные демонстрационные товары, которые добавляются только при отсутствии соответствующих ID. Эти записи не должны восприниматься как подтверждённые коммерческие цены и остатки. Существующие записи не перезаписываются.

Транзакционный API требует `place_order(...)` и столбец `orders.stock_reserved`. Поэтому SQL-миграцию нужно применить **раньше**, чем публиковать обновлённый API.

В Authentication → URL Configuration:

- Site URL: реальный HTTPS-origin сайта.
- Redirect URLs: тот же origin и точный URL `/reset-password` на нём.
- Не используйте неизвестные wildcard-домены. Для отдельного staging добавьте только его доверенные адреса.
- Для production оставьте подтверждение email, если оно нужно бизнес-процессу. При регистрации без мгновенной сессии сайт показывает просьбу подтвердить почту.

Администратора назначайте только через доверенный SQL Editor после регистрации собственного пользователя: обновите `public.profiles.role` на `admin` для ID этого пользователя из `auth.users`. Обычный клиент не может повысить свою роль — это проверено с RLS.

## 3. Задайте переменные

Предпочтительно используйте защищённые настройки окружения хостинга. Для своего сервера допустим локальный `.env` в корне приложения, недоступный посторонним пользователям и не добавленный в Git. `.env.example` — только перечень: его шаблонные значения нужно заменить. Не выполняйте `source .env` в shell; Node и Vite читают его сами.

| Переменная | Где нужна | Значение |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | При сборке frontend | URL вашего проекта Supabase |
| `VITE_SUPABASE_ANON_KEY` | При сборке frontend | Публичный anon/publishable key |
| `SUPABASE_URL` | Runtime API | URL того же проекта |
| `SUPABASE_SERVICE_ROLE_KEY` | Только runtime API | Серверный service_role/secret key |
| `TELEGRAM_BOT_TOKEN` | Runtime API | Токен существующего бота |
| `TELEGRAM_CHAT_ID` | Runtime API | ID чата администратора |
| `RESEND_API_KEY` | Runtime API | Ключ Resend с разрешением отправки |
| `ADMIN_EMAIL` | Runtime API | Получатель уведомлений |
| `FROM_EMAIL` | Runtime API | Подтверждённый отправитель Resend |
| `PORT` | Свой Node-сервер | Порт, по умолчанию 3000 |
| `NODE_ENV` | Свой Node-сервер | `production` |

Секреты никогда не должны иметь префикс `VITE_`: такие значения попадают в публичный JavaScript. Изменение публичных переменных требует новой сборки; runtime-переменных — перезапуска процесса/нового deployment.

Для Telegram администратор должен запустить бота или добавить его в чат с правом отправки. Телефон +996502820642 используется для контакта с человеком и не заменяет токен/ID чата.

В Resend подтвердите sender/domain и настройте DNS по значениям из своего аккаунта. Тестовый отправитель `onboarding@resend.dev` ограничен правилами Resend и не является готовой production-настройкой.

При ограниченной исходящей сети разрешите HTTPS к точному hostname проекта Supabase, `api.telegram.org` и `api.resend.com`. Переходы посетителей к `t.me`, `wa.me` и карте выполняются их браузерами.

## 4. Установите зависимости и проверьте сборку

Из корня приложения:

```sh
npm ci --include=dev
npm test
npm run test:db
npm run test:http
npm run build
npm run test:e2e
npm run test:production
npm run check:services
```

Для браузерных тестов установите Chromium: `npx playwright install chromium`, если системного Chromium нет. Дополнительно, на машине с Docker: `npm run test:postgres`. Эта команда создаёт отдельный PostgreSQL без сети и опубликованных портов, проверяет реальную конкуренцию и удаляет только свой контейнер. Она не подключается к существующим базам.

`check:services` не регистрирует пользователей, не создаёт заказы, не меняет остатки и не отправляет сообщения. Он проверяет конфигурацию, доступность таблиц Supabase, Telegram `getMe`/`getChat` при наличии ключей. Код выхода 2 означает отсутствующие/непригодные настройки или неуспешную проверку. Проверка конфигурации Email не доказывает доставку письма. Даже код 0 не заменяет контрольный заказ и проверку реального inbox/чата.

`npm run test:production` проверяет уже построенный `dist`, а не dev-server Vite. Его API — настоящие обработчики Express, без подмены ответов. Без ключей регистрация и успешный заказ в настоящем Supabase остаются непроверенными.

## 5. Проверенный вариант: Node-сервер

После сборки:

```sh
NODE_ENV=production PORT=3000 npm start
```

Одна команда раздаёт `dist`, обслуживает SPA-маршруты и `/api/order`, `/api/booking`, `/api/health`. Исходники и `.env` не раздаются как статика. Это отличается от `npm run preview`: preview — средство проверки Vite; для его API отдельно нужен `npm run api`.

На своём сервере запустите процесс через process manager/systemd с автоматическим восстановлением. Укажите:

- WorkingDirectory: абсолютный путь к корню приложения.
- Команда: `npm start`, используя установленный Node.js 24.
- Переменные: `NODE_ENV=production`, `PORT=3000` и все runtime-значения из таблицы выше.
- Рабочий пользователь: отдельная учётная запись, имеющая доступ к приложению и `.env`, без запуска сайта от root.

Перед Node-сервером настройте HTTPS через хостинг или reverse proxy. Для nginx внутри существующего HTTPS server-блока:

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 60s;
}
```

Сертификат и домен должны принадлежать вам; их значения в проекте не придуманы. Публичный порт Node ограничьте локальным доступом/firewall либо внутренней сетью платформы. Маршрутизируйте **и страницы, и `/api`** на тот же процесс, не только `dist`.

После сборки можно исключить devDependencies для runtime: Express находится в production dependencies. Если выполняете `npm prune --omit=dev`, последующая пересборка/тесты потребуют снова установить devDependencies.

## 6. Вариант Vercel

В настройках проекта:

- Root Directory: `dentalcare-shop`.
- Framework: Vite; Node.js: 24.x.
- Install Command: `npm ci --include=dev`.
- Build Command: `npm run build`.
- Output Directory: `dist`.
- Добавьте public build-time и private runtime-переменные из таблицы, примените SQL-миграцию до публикации.

Используйте существующий `vercel.json`; API-файлы становятся serverless functions. `npm start` в этом варианте не используется. Развёртывание в вашем аккаунте Vercel и его доступ к базе в этой среде не проверялись. Проверенный локально production-путь — Node-сервер из предыдущего раздела.

## 7. Обязательная проверка после подключения настоящих сервисов

1. Откройте сайт по HTTPS, обновите `/shop/p1` и `/booking` напрямую; не должно быть 404 SPA.
2. Проверьте `/api/health`: `ok` означает работу процесса, а `configuration` — только наличие пригодных значений, **не доступность сервисов**.
3. Зарегистрируйте собственный проверочный аккаунт, подтвердите email, войдите, сохраните профиль и проверьте восстановление пароля. Подтвердите роль администратора через SQL Editor и вход в админку.
4. На staging или с согласованным товаром запишите исходный остаток N. Оформите один заказ на 1 единицу: в базе должен появиться один заказ, сумма должна совпасть с ценой базы, остаток стать N−1. Историю не удаляйте.
5. Отмените заказ в админке: остаток должен стать N. Повторная отмена не должна увеличивать его ещё раз. При повторной активации должен вернуться N−1, если товар доступен.
6. Проверьте фактическое сообщение в Telegram и письмо на `ADMIN_EMAIL`, а не только ответ API. При ошибке уведомлений уже сохранённый заказ не нужно отправлять заново.
7. Проверьте обычного пользователя: он не должен видеть чужие заказы или админку и не может изменить свою роль.
8. Повторите покупки, меню, обе темы и перезагрузку на настоящем телефоне и в Safari, если поддержка этих устройств обязательна.
9. Подтвердите реальные реквизиты клиники, фотографии, цены и остатки. В исходном проекте есть образцы, которые не заменяют ваши коммерческие данные.

Онлайн-оплата картой не была реализована в исходном проекте и не имитируется; текущий процесс оформляет заявку/заказ и уведомляет администратора.

## Восстановление конфигурации авторизации

Поддерживаются публичные ключи legacy anon JWT и `sb_publishable_*`. Дополнительное имя build-переменной: `VITE_SUPABASE_PUBLISHABLE_KEY`. При отсутствии build-пары браузер до инициализации состояния получает публичную пару из `/api/public-config`; для неё задайте runtime `SUPABASE_URL` и `SUPABASE_ANON_KEY` или `SUPABASE_PUBLISHABLE_KEY`. Серверный `SUPABASE_SERVICE_ROLE_KEY` по-прежнему нужен для доверенного API заказов и никогда не публикуется этим endpoint. `check:services` учитывает публичные aliases, а health отдельно сообщает флаг `authentication`. Успех получения настроек не доказывает существование schema, аккаунта или admin-роли.
