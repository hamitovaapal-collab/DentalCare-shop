## Что нужно проверить в вашей базе

1. Войти в сайт аккаунтом владельца. Пароль не присылать в чат.
2. В доверенном Supabase Dashboard открыть Authentication → Users, найти именно этот аккаунт по email и скопировать его ID.
3. В Table Editor → profiles найти строку с **тем же ID** и проверить role. Для владельца, которому разрешено управление магазином, установить admin через Dashboard. Не назначать admin всем пользователям и не менять RLS.
4. Если строки profiles нет, сначала восстановить профиль конкретного подтверждённого владельца через доверенный SQL Editor/сервер. Не создавать фиктивный аккаунт и не назначать права первому попавшемуся пользователю.
5. Вернуться на /admin и нажать повторную проверку либо обновить страницу.

Администратор назначается в базе, а не в frontend-коде. В текущей среде нет доступа к пользовательской Supabase, поэтому фактическая роль вашего аккаунта неизвестна и не изменялась.

## Публикация и границы проверки

Для публичного домена нужно опубликовать текущую исправленную версию в существующий Netlify-проект, с конфигурацией из NETLIFY.md. Изменения рабочей копии не появляются там автоматически. У этой сессии нет доступа к аккаунту Netlify; живая версия также недоступна через ограниченный сетевой прокси.

Браузерные проверки используют изолированный контракт Supabase: переход из шапки, вход с возвратом в /admin, блокировка обычного пользователя, обновление роли в существующей сессии и прежние 20 сценариев аккаунта/админки. Они не подтверждают роль реального аккаунта в вашей базе. Production-сборка проверяется отдельно.

Итог текущего прогона: **23/23 браузерных проверки прошли**, production-сборка и `git diff --check` успешны.

## Восстановление публичной конфигурации при запуске

Клиент сначала использует публичные build-настройки `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` / `VITE_SUPABASE_PUBLISHABLE_KEY`. При отсутствии подходящей пары перед созданием AppProvider запрашивает `/api/public-config` с таймаутом 2,5 секунды. Endpoint поддерживается Express и Netlify Functions, использует только публичные переменные и не кешируется. Для runtime можно использовать `SUPABASE_URL` и `SUPABASE_ANON_KEY` / `SUPABASE_PUBLISHABLE_KEY`.

Неподключённая база возвращает `{configured:false}` без HTTP-ошибки: дүкөн продолжает работать, /admin честно сообщает о необходимости подключения. Это не создаёт проект, пользователя или роль. Секретные ключи не принимаются как публичные; build останавливается до включения приватного ключа в assets. Service-role credential никогда не используется как запасной ключ браузера.

На текущем этапе все варианты настоящих настроек отсутствуют в рабочей среде, нет Netlify/Supabase CLI-сессий или подключённых аккаунтов, секретных bindings тоже нет. Доступ к GitHub позволяет публиковать код, но не заменяет доступ к этим сервисам. Аккаунт владельца и admin-роль в настоящей базе ещё не созданы/не подтверждены.
